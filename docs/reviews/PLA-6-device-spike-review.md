## Required corrections

**R1 — Separate forced updating from unattended updating and GMS.** RESULT S4 correctly describes forced jobs, but its consequence says this keeps “both apps and GMS updating.” GMS is absent from the version-change list. The current feasibility questions and verification matrix explicitly require a separate unattended 72-hour run with an unrestricted comparison. Keep S4 as a successful background-update diagnostic; mark unattended operation and GMS updating not shown by this spike. Do not turn the observed Phone update failure (1055, untraced) into an implied all-approved-apps pass. No need to rerun the already-proven 23-package diagnostic merely to correct wording.

**R2 — A single crash recovery is not a closed escape window.** RESULT A5 calls the Moto-launcher-hidden fallback “closed.” `evidence/a5/crash-fallback.txt` has BLOCK **off**, one induced crash, a lock-task exit/reentry, and polling starting at +2 seconds. It measures roughly 0.51 seconds to reentry but does not attempt a queued notification, deep link, explicit launch or repeated crash in that interval. Replace “closed/fixes it” with “single-crash recovery shortened in this configuration; escape during recovery not tested.” Reproduce the existing baseline with `tools/a4-crash.sh` and its recorded configuration; a future stronger test must race an unapproved fixture during repeated crashes with BLOCK on. That future test belongs on a dedicated emulator, not a casual phone replay.

**R3 — Process creation is not proof Application.onCreate ran.** S7's process-start timestamp proves the hide did not prevent process creation. It does not show completion of application binding, onCreate, network work, or visible UI. Replace “onCreate … did run” with “process started; application-code execution not instrumented.” Likewise “no Displayed line” is absence of that log, not frame-by-frame proof no UI ever appeared. Report one measured race, not a bound for all future installs. The watcher is reactive and was tested only while lock task was off.

**R4 — Correct misleading totals and status summaries.** `evidence/a5/hide-results.txt` records **20 total packages, including the three Facebook service/installer packages**; adding Moto launcher makes the 21 in A6/A7. “20 extras + 3 Facebook” double-counts them. The “every app's Google sign-in goes through GMS” summary overstates Slack: its own control shows the same error without lock task and no activity start. The opening B-Q4 sentence saying only Telegram is done is stale against the later five-app tables. Keep app/version-specific observations and label “nothing core breaks” as the limited UI smoke check.

**R5 — Account for the exported test dispatcher.** `dpc/app/src/main/AndroidManifest.xml:21` exports MainActivity without a permission; `MainActivity.kt:107–112` consumes `op=crash`, `lt-stop`, and `launch` from either onCreate or onNewIntent. DUMP protects CommandReceiver, but does not protect this alternate entry. Android documents that an exported activity without a permission can be launched by other apps: [activity manifest reference](https://developer.android.com/guide/topics/manifest/activity-element#exported).

Static reproduction for an ordinary foreground fixture is `startActivity(Intent().setComponent(ComponentName("com.plainphone.spike.dpc", "com.plainphone.spike.dpc.MainActivity")).putExtra("op", "crash"))`. The spike is already allowlisted. The receiver is bypassed entirely. **Code-confirmed attack surface; not replayed from an unprivileged fixture in this review.** Do not claim a sustained lt-stop escape: onResume may relock. The visible RELEASE/Stop buttons are also intentional spike exits. This throwaway harness is deliberately not a restricted-user product. Document that boundary; remove or isolate the dispatcher before any production reuse or security demonstration relying on it.

## Independent Escape Artist probes

**E1 — Outlook accepted route: confirmed.** On Outlook 5.2639.2, open Add account → PRIVACY AND TERMS → Privacy & Cookies → scroll to the U.S. Department of Commerce Data Privacy Framework link. Its public DPF site loads inside `com.acompli.acompli.GenericWebViewActivity` while `mLockTaskModeState=LOCKED`. See `outlook-offsite.png` and device-review.log in the archive. This corroborates the original step-05 transcript. Beaux's recorded acceptance on [PLA-14](/PLA/issues/PLA-14), Telegram 4463 / ADR Risk 3, stands. I did not sign in/out to re-prove the post-sign-out variant.

**E2 — Easier Outlook routes sought; no easier general-browser escape established.** Probed the welcome-screen Create new account entry (Microsoft registration screen in Outlook, no credentials submitted), the privacy-page Microsoft logo, and Privacy → Home → All Microsoft → Other → Microsoft Rewards → Earn. The latter traversed public Microsoft pages and ended at Microsoft sign-in inside the same Outlook WebView. No Bing search or arbitrary destination was reached. These extend the navigable surface but do not establish a materially easier leak than the accepted route. This is a bounded search, not an exhaustive no-bypass claim. Do not report the provisional screenshot filename as a Bing success. Any later easier route still needs Beaux's decision.

**E3 — Gmail Microsoft in-page recovery: newly confirmed reachable, general browsing not shown.** Open Gmail's Add account setup → Outlook, Hotmail, and Live → Forgot your username? → Recover your username. The live recovery form stays inside Gmail `.setup.AccountSetupFinalGmail`, with lock task LOCKED. I entered nothing. Help opens an in-page help pane; the Microsoft Support link attempts Chrome and yields BlockedAppActivity. The initial center-of-bounds tap missed the wrapped link; tapping its actual second line produced the block (`gmail-support-result.png`). Create an account was tapped twice but no navigation was observed; record that as unresolved rather than proof it is blocked. This supplements the original blocked Privacy link. No inbox or email was opened; setup was entered directly using the same CREATE_NEW_ACCOUNT activity the author's trace identified.

**E4 — Emergency-information lead: inconclusive.** The allowlisted emergency dialer screen opened under BLOCK. Tapping Emergency information twice left the same top activity/LOCKED readback. I did not inspect medical/contact data, press a dial key or place a call. A no-navigation observation does not close that route or certify emergency access.

The behavior distinction between activity launches and in-app navigation is consistent with the [Android lock-task guide](https://developer.android.com/work/dpc/dedicated-devices/lock-task-mode) and the [BLOCK feature reference](https://developer.android.com/reference/android/app/admin/DevicePolicyManager#LOCK_TASK_FEATURE_BLOCK_ACTIVITY_START_IN_TASK). The source supports activity-level controls; containment of these specific WebViews rests on the recorded device probes.
